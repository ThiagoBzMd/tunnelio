# Tunnelio — Protocol and Data Model Specification

**Specification revision:** 1.9 · **Date:** 2026-10-18
**Protocol version:** `1` · **Status:** implemented and in production; rev. 1.1 adds images; rev. 1.2 adds the single password (login key + vault derived in the browser), pairing synchronization, `history_import` and the "where the conversations are kept" switch; rev. 1.3 **removes cloud storage** (conversations only on the computer), adds e-mail verification at sign-up, reset by code, an optional second factor and the rule "changing/resetting the password disconnects everything"; rev. 1.4 adds documents in the chat (extracted in the browser, §7.7) and `history_clear`; rev. 1.6 adds the anonymous chat (`mode:"incognito"`) and the Ollama library served by the server; rev. 1.7 adds the encrypted preferences in the account and the active sessions (§10.5); rev. 1.8 adds agents and skills kept on the computer (§9.4) and six types in the allowlist; rev. 1.9 adds agent chains (§9.4, history schema 4), the update notice in the relay's `welcome` (§3.4), a model memory that follows what Ollama loaded (§7.7), downloads in one click that outlive the session (§7.3) and the download size of each model in the library (§11.1) (all without a bump of `v`).

> **About the "rev." labels.** They number the revisions of this specification, so each feature or field says when it arrived (rev. 1.1 to rev. 1.9). They are not version numbers of the apps: the computer app and the server are released separately, each with its own number ([Semantic Versioning](https://semver.org), 1.0.0 at the first public release). The wire protocol has its own version, `v: 1` (§12).

> This document is the **contract** between the three parts of the system. The cryptographic
> protocol is implemented **twice** (Go in the tray, TypeScript in the browser);
> the server (Django) implements **only** the relay layer and the REST APIs, and
> **never** touches channel cryptography. Everything that is byte-exact is fixed here and
> covered by test vectors in [`docs/vectors/vectors.json`](vectors/vectors.json),
> generated by [`docs/vectors/gen_vectors.py`](vectors/gen_vectors.py).
>
> The keywords **MUST / MUST NOT / MAY** follow the meaning of RFC 2119.

## 0. Scope, notation and constants

### 0.1 Parts

| Part | Directory | Language | Role |
|---|---|---|---|
| **Tray** (*device*) | `tray/` | Go | Runs on the user's computer; talks to the local Ollama and to the relay. |
| **Web** (*client*) | `web/` | TypeScript | SPA in the browser; all user-side cryptography. |
| **Server** (relay + accounts) | `server/` | Python/Django | Authenticates, registers devices, **forwards bytes** blindly, stores encrypted blobs. |

### 0.2 Notation

- `||` byte concatenation. `len8le(x)` = length of `x` as 8 bytes little-endian (only in SPAKE2, inherited from RFC 9382).
- Quoted strings are ASCII/UTF-8 **without** a terminator.
- `b64url(x)` = base64url **without padding** (RFC 4648 §5). All binary fields in JSON use `b64url`.
- `hex(x)` in the test vectors.
- Integers in JSON are JSON numbers; 64-bit counters never go beyond 2^53 in practice (enforced limit, §6.3).

## 1. Overview and threat model

### 1.1 Flow

```
┌──────────────┐  WSS (cookie)   ┌──────────────────┐   WSS (device token)  ┌──────────────┐
│  Browser     │────────────────▶│  Server (relay)  │◀──────────────────────│  Tray (Go)   │
│  web/ (TS)   │◀────────────────│  Django Channels │──────────────────────▶│  on computer │
└──────┬───────┘                 └──────────────────┘                       └──────┬───────┘
       │  E2E: SPAKE2 (pairing) → X25519+HKDF (session) → AES-256-GCM (envelopes)    │
       └──────────────────────────────────────────────────────────────────────────────┘
                                                                                     │ HTTP
                                                                              ┌──────▼───────┐
                                                                              │ Ollama local │
                                                                              │ 127.0.0.1:11434
                                                                              └──────────────┘
```

Three layers, from the outside in:

1. **Relay** (§3) — WebSocket + JSON in plaintext **with routing metadata only**. The server reads `type`, `device_id`, `client_id`, `claim` and sizes. It never reads `payload`.
2. **E2E session** (§4–§6) — pairing by SPAKE2 establishes a **pairing key `PK`** (32 bytes) per pair (browser, device). Each connection derives **ephemeral** keys (X25519 authenticated by `PK`) and encrypts each message with AES-256-GCM and a sequential nonce.
3. **Application** (§7–§10) — encrypted JSON messages with a **closed allowlist** in the tray; each type maps to a fixed Ollama endpoint.

### 1.2 Principle: the server is blind

- The server **and whatever sits in front of it** (a CDN, tunnel or reverse proxy) see: ciphertext, sizes, times, who talks to whom.
- The server does **not** route by model, does not load-balance, does not read requests, does not know model names, titles or content.
- The choice of device and model happens in the UI; the device is a **routing address** (unavoidable metadata); the model goes **inside the ciphertext**.

### 1.3 What the server knows (closed and documented list)

| Data | Where | Why |
|---|---|---|
| Email, Argon2id hash of the password, creation/login dates | `accounts.User` | Authentication |
| Devices: name (given by the user), platform, tray version, dates of creation and last contact, token hash | `devices.Device` | Device list, revocation |
| Pairing sessions: 4-symbol *claim*, state, expiry (5 min) | `devices.PairingSession` | SPAKE2 routing (the 8-symbol secret **never** reaches the server) |
| Online/offline presence (ephemeral, cached) | relay | Show status in the UI |
| Connection logs: user, device, kind, connected/disconnected at, bytes and frames in each direction, close code | `relay.ConnectionLog` | Operations and abuse; **7-day retention**; **no IP** (the proxy in front already sees it) |
| Synced pairings: **one** opaque blob per account (size, date) | `pairings.PairingsBlob` | A new browser gets in without a code (§10.2) |
| E-mail codes: HMAC of the code, purpose (`verify`/`reset`), validity, attempts | `accounts.EmailCode` | Confirm the e-mail at sign-up; password reset |
| Second factor: **encrypted** TOTP seed, confirmed, last accepted step, failures, lockout | `accounts.TotpSecret` | Two-step login (optional) |
| The person's preferences: **one** opaque blob per account (size, date) | `preferences.PreferencesBlob` (rev. 1.7) | Theme, language, chosen name etc. in any browser (§10.5) |
| Active sessions: browser, system and kind of device **as the browser itself announces it** (`User-Agent`), creation and last use; **no IP, no location** | `accounts.LoginSession` (rev. 1.7) | List of sessions with "Sign out" (§10.5) |

Nothing beyond that. Of this data, the Django admin exposes only non-sensitive fields (sizes, dates, counts) — the `ciphertext` and the `token_hash` are excluded from forms and listings.

### 1.4 Threats considered

| Threat | Mitigation |
|---|---|
| Curious server (or the proxy in front) reads content | E2E: the server never has `PK` or session keys. |
| **Tampered** server (or the proxy in front, or the machine) serves modified JavaScript | **Not mitigated by E2E**: the browser runs the code the server delivers, and that code sees the password and the conversations. A limit of all E2E on the web. Mitigation (detection, not prevention): the code is public, the server publishes the public commit its web app was built from (`/version.json`), the build is reproducible and `scripts/verify-build.sh` rebuilds it from that commit and compares every file byte for byte with what is served; in the future, a native client. |
| Leak of the database (or of a backup) + weak password | **Offline** guessing against the pairings blob and the login hash; each attempt costs a 64 MiB Argon2id (§10.1). Minimum of 12 characters, a list of common passwords and, since rev. 1.9, a strength check in the browser (zxcvbn-ts with leaked passwords and English/Brazilian Portuguese words and names; a new password needs score ≥ 3, "safely unguessable" against offline guessing of a slow hash; the e-mail counts against it); the second factor does not help here. |
| Malicious server attempts MITM on the pairing | SPAKE2: without the code, 1 online attempt per pairing session; failure → code invalidated. No offline attack (PAKE). |
| Server replays old frames (*replay*) | Sequential nonce per direction and per session; ephemeral keys per connection; out-of-order counter → discard. |
| Server delivers a frame from A to B | AAD includes `device_id`; keys are per session; does not decrypt → discard. |
| Compromised browser | Has the `PK` of that pairing: can talk to the paired device within the limits of the allowlist. Revocation = remove the device (web) or remove the pairing (tray menu). |
| Malicious message reaches the tray | Closed allowlist, validated structs, no raw JSON to Ollama, no `os/exec` in the channel module, `/api/create|push|copy` unreachable. |
| Theft of the device token | The token only authenticates the relay connection; without `PK` it decrypts nothing. Rotation = remove and pair again. |
| Loss of the pairing in the browser | Comes back through synchronization when signing in with the password (§10.2); if the password changed or the device was removed, pair again with the code from the tray. |
| Loss of the login password | Code by e-mail (§11.2) → new password → **everything disconnected** (§10.3); the history on the computer does not depend on the password. Without e-mail configured, only the administrator resets it. |
| DoS on pairing (guessing the *claim*) | A single join per code; rate limit per user/IP; 5 min expiry. |

## 2. Identifiers and encodings

| Identifier | Format | Who generates it | Notes |
|---|---|---|---|
| `device_id` | UUID v4, canonical lowercase `8-4-4-4-12` text; raw form = 16 bytes | **Server**, when the first pairing completes | Routing address. Goes into the envelope AAD (raw form). |
| `client_id` | 16 hex symbols, opaque | **Relay**, per client WebSocket connection | Lives only while the connection exists. |
| `pairing_id` | 16 bytes, `b64url` | **Derived** from `PK` (§4.6) | Identifies *which* pairing (browser) the tray must use in the session. |
| `claim` | 4 Crockford symbols | **Server**, per pairing session | Pairing routing; not a secret. |
| `secret` | 8 Crockford symbols (40 bits, CSPRNG) | **Tray** | Never leaves the tray except through the screen/QR. |
| `conversation_id` | UUID v4 | **Browser** | Same space in both history modes. |
| request `id` | string ≤ 64 chars, unique per session | **Browser** | Correlates request/response/stream. |

### 2.1 Crockford base32

Alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (no I, L, O, U). **Input** is normalized: uppercase, remove `-` and spaces, map `I→1`, `L→1`, `O→0`. **Output** is displayed in groups of 4 separated by `-`.

- **Pairing code:** 12 symbols = `claim(4) || secret(8)`, displayed `CCCC-SSSS-SSSS`.
- **Recovery code (rev. 1.1–rev. 1.2, unused since rev. 1.3):** 32 bytes → big-endian integer → **52 symbols** (5 bits each, left-padded with zeros) **+ 1 check symbol** (`n mod 37`, alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ*~$=U`) = 53 symbols, displayed in groups of 4.

Vector: `V6_crockford_base32`.

### 2.2 Pairing QR

The tray MAY display a QR containing the URL `https://<host>/pair#<CODE>` (12 symbols without hyphens). The code goes in the **fragment** (`#`), which the browser **does not send** to the server. The SPA reads the fragment, requires login if needed (preserving the fragment on the client side) and conducts the pairing. This removes the need for a camera library: the phone's camera app opens the URL.

## 3. Relay layer (transport)

### 3.1 Principles

- The relay **has no business logic**. It: authenticates the connection, maintains presence, creates/destroys sessions (`client_id`×`device_id` pairs), forwards `payload` without inspecting it, enforces limits, records metadata.
- Small, documented interface so that it can be **rewritten in Go as a sidecar** without changing tray, web or the other Django apps (see §3.9).
- All WebSocket frames are **text** containing **one JSON object** with a `type` field. Binary frames are reserved (v2: binary framing).

### 3.2 Endpoints

| Endpoint | Who connects | Authentication |
|---|---|---|
| `wss://<host>/ws/client` | Browser (and, in v2, API clients) | Django session cookie (`SameSite=Lax`, `Secure`, `HttpOnly`) + check of `Origin` against `CSRF_TRUSTED_ORIGINS`. v2: `Authorization: Bearer <api_token>`. |
| `wss://<host>/ws/device` | Tray | `Authorization: Bearer <device_token>` header. **No header** = *unpaired* mode: only `hello`, `pair_*`, `ping` frames are accepted. |

WebSocket subprotocol: `tunnelio.v1` (the server MUST refuse with 4002 if the client asks for another one).

### 3.3 Frames — client side (`/ws/client`)

| Direction | `type` | Fields | Semantics |
|---|---|---|---|
| C→S | `hello` | `v:1`, `app:"web"`, `version:"<semver>"` | Mandatory first frame. |
| S→C | `welcome` | `v:1`, `client_id`, `devices:[{device_id,name,online}]`, `limits:{max_frame_bytes}` | Response to `hello`. |
| C→S | `open` | `device_id` | Opens a session with an online device of the same user. |
| S→C | `opened` | `device_id` | Session created (the tray received `session_open`). |
| C→S | `close` | `device_id` | Ends the session. |
| S→C | `closed` | `device_id`, `reason` | Session ended (by the client, by the device or by a drop). |
| C→S | `data` | `device_id`, `payload:{…}` | Forwarded to the device as `data{client_id, device_id, payload}`. Requires an open session. |
| S→C | `data` | `device_id`, `payload:{…}` | Coming from the device. |
| C→S | `pair_join` | `claim` | Joins a pairing session (§4.2). |
| S→C | `pair_joined` | `claim`, `device_id?` | Accepted (`device_id` present if the device already belongs to the account). |
| C↔S | `pair_msg` | `claim`, `payload:{…}` | Opaque SPAKE2 messages, forwarded. |
| S→C | `pair_result` | `claim`, `ok`, `device?:{device_id,name}`, `code?` | Final result reported by the device. |
| S→C | `device_status` | `device_id`, `online` | Presence changed. |
| C↔S | `ping` / `pong` | `t` (ms epoch, echo) | Keepalive. |
| S→C | `error` | `code`, `message?`, `ref?` | Relay error (never about content). |

### 3.4 Frames — device side (`/ws/device`)

| Direction | `type` | Fields | Semantics |
|---|---|---|---|
| D→S | `hello` | `v:1`, `app:"tray"`, `version`, `platform:"windows"\|"macos"\|"linux"`, `protocol_versions:[1]` | Mandatory first frame. `platform`/`version` are stored in the `Device`. |
| S→D | `welcome` | `v:1`, `device_id` (or `null` if unpaired), `limits`, `latest?:{version,url}` | `latest` (rev. 1.9): the newest computer-app release, only when the server is configured with it (`TRAY_LATEST_VERSION` + an `https://` `TRAY_DOWNLOAD_URL`). A tray whose own version is an older release shows "New version … — download" in its menu and one notification per version; a build from source (`dev…`) never does. The tray opens only `https://` pages. |
| D→S | `pair_start` | — | Requests a pairing session. |
| S→D | `pair_ready` | `claim`, `expires_at` | The tray composes and displays `claim || secret`. |
| S→D | `pair_joined` | — | A browser joined. Exactly **one** per session. |
| D↔S | `pair_msg` | `payload:{…}` | Opaque SPAKE2. |
| D→S | `pair_done` | `ok`, `name?` (suggested device name, e.g. hostname) | **Only the device decides**. `ok:true` on the 1st pairing → the server creates the `Device` and replies `paired`. |
| S→D | `paired` | `device_id`, `device_token` | Only on the first pairing. The tray persists both and starts using the token. The current connection is already considered authenticated. |
| S→D | `pair_aborted` | `reason` | Expired/aborted. |
| S→D | `session_open` | `client_id` | A browser opened a session. |
| S→D | `session_closed` | `client_id`, `reason` | |
| S→D | `data` | `client_id`, `device_id`, `payload:{…}` | |
| D→S | `data` | `client_id`, `payload:{…}` | The relay routes it to the `client_id` connection. |
| D→S | `close` | `client_id` | The device ends the session (e.g. counter violation, §6.3). The relay replies `session_closed{client_id, reason:"device"}` and notifies the client with `closed{reason:"device"}`. |
| S→D | `revoked` | `reason` | Device removed/account deleted; followed by close 4001. |
| D↔S | `ping` / `pong` | `t` | |
| S→D | `error` | `code`, `message?` | |

### 3.5 WebSocket close codes

| Code | Meaning |
|---|---|
| 4001 | Unauthorized (invalid session, invalid/revoked token) |
| 4002 | Protocol violation (invalid JSON, missing `hello`, wrong subprotocol, unknown type) |
| 4003 | Persistent rate limit (also used for `E_LIMIT`: too many connections per user) |
| 4004 | Frame larger than the limit |
| 4005 | Server shutting down (reconnect) |
| 4006 | Replaced (the same device connected again; the old connection is closed) |

### 3.6 Relay error codes (`error.code`)

`E_AUTH`, `E_INVALID`, `E_VERSION`, `E_RATE_LIMIT`, `E_TOO_LARGE`, `E_NOT_FOUND` (device is not yours / does not exist), `E_DEVICE_OFFLINE`, `E_NO_SESSION`, `E_PAIR_NOT_FOUND`, `E_PAIR_BUSY` (already has a browser), `E_PAIR_EXPIRED`, `E_PAIR_FAILED`, `E_LIMIT` (too many devices/connections).

### 3.7 Presence, sessions and keepalive

- **Online** = authenticated and live device connection **that has received its `welcome`**: the relay announces the device (and routes `session_open` to it) only after the `welcome`, because browsers open a session the moment a device shows up and the tray expects the `welcome` first. A device has **one** connection; the new one replaces the old one (4006), also at the `welcome`. The replaced tray waits for the maximum backoff (60 s) before trying again, so as not to compete with the other instance. Changes generate `device_status` to all of the owner's client connections.
- **Session** = (`client_id`, `device_id`) pair. Created by `open`, destroyed by `close`, by a drop on either side or by revocation. A client can have sessions with several devices; each pair has its own cryptographic state (§5).
- **Keepalive:** both sides send `ping` every 30 s; the server replies `pong`. The server closes a connection with **no** frame for 90 s. Client/tray consider the connection dead with no `pong` for 45 s. (CDNs and tunnels commonly drop idle WebSockets after about 100 s — hence the margin.)
- **Reconnection (tray and web):** exponential backoff with full *jitter*: base 1 s, ×2 up to 60 s; resets after 60 s stable. On reconnecting, the tray redoes `hello`; the previous E2E sessions are discarded and the browser redoes the handshake (§5) when it receives `device_status online`.

### 3.8 Limits and rate limit (relay)

| Limit | Default | Env |
|---|---|---|
| Maximum frame | 8 MiB | `RELAY_MAX_FRAME_BYTES` |
| Client: frames | 20/s sustained, burst 60 | `RELAY_CLIENT_FPS` |
| Device: frames | 60/s sustained, burst 200 (token streaming) | `RELAY_DEVICE_FPS` |
| Bytes per connection | 64 MiB/min | `RELAY_BYTES_PER_MIN` |
| Client connections per user | 10 | `RELAY_MAX_CLIENTS_PER_USER` |
| Devices per user | 20 | `DEVICES_MAX_PER_USER` |
| Open sessions per client | 5 | `RELAY_MAX_SESSIONS_PER_CLIENT` |
| `pair_join` | 5/min per user (per address: whatever the proxy in front enforces) | `PAIR_JOIN_RATE` |
| `pair_start` | 3/min per device | — |
| Pairing session | expires in 5 min | `PAIR_TTL_SECONDS` |

Exceeding a limit generates `error E_RATE_LIMIT` (with `retry_after_ms`) and, if it persists for 10 s, close 4003.

### 3.9 Minimal relay interface (for reimplementation)

From the rest of the system, the relay needs exactly three operations and one event:

```
authenticate_client(cookie, origin)        -> user_id | None
authenticate_device(bearer_token)          -> device_id, user_id | None     # SHA-256(token) == Device.token_hash (deleted row = revoked)
pairing_bind(claim, device_name, user_id)  -> device_id, device_token       # creates Device on the 1st pairing (idempotent for an already paired one)
on_connection_closed(metadata)             -> writes relay.ConnectionLog
```

And the relay exposes to the rest: `is_online(device_id)` and `disconnect_device(device_id, reason)` (used by DELETE /api/devices/{id} and by account deletion). In the Django implementation this is the `relay` app (Channels consumers + a group per user `user.<id>` and per device `device.<id>`). A Go sidecar would make the same four calls over internal HTTP.

## 4. Pairing — SPAKE2

### 4.1 Decision

**SPAKE2 with a short code** (12 symbols, 40 bits of secret) is the choice for v1. Rationale in §14.1. Fallback (not implemented): a 32-byte key displayed as QR/base32.

Ciphersuite: **SPAKE2-P256-SHA256-HKDF-HMAC** exactly as in RFC 9382, with `A = "client"`, `B = "device"`, `AAD = "tunnelio/v1"`. The browser is **A** (sends first, uses `M`); the tray is **B** (uses `N`).

### 4.2 Flow

```
Tray                           Relay                          Browser (logged in)
 │ pair_start                    │                                │
 │──────────────────────────────▶│                                │
 │ pair_ready{claim}             │                                │
 │◀──────────────────────────────│                                │
 │ shows  CCCC-SSSS-SSSS (+QR)   │                                │
 │                               │   pair_join{claim}             │  (user types the code;
 │                               │◀───────────────────────────────│   ONLY the claim goes to the server)
 │ pair_joined                   │   pair_joined{claim}           │
 │◀──────────────────────────────│───────────────────────────────▶│
 │                               │   pair_msg{claim, pake1{pA}}   │
 │ pair_msg{pake1}               │◀───────────────────────────────│
 │◀──────────────────────────────│                                │
 │ pair_msg{pake2{pB,cB}}        │                                │
 │──────────────────────────────▶│   pair_msg{claim, pake2}       │
 │                               │───────────────────────────────▶│  verifies cB
 │                               │   pair_msg{claim, pake3{cA}}   │
 │ pair_msg{pake3}               │◀───────────────────────────────│
 │◀──────────────────────────────│                                │
 │ verifies cA                   │                                │
 │ pair_done{ok:true, name}      │                                │
 │──────────────────────────────▶│  creates Device (1st time)     │
 │ paired{device_id, token}      │   pair_result{ok, device}      │
 │◀──────────────────────────────│───────────────────────────────▶│  persists PK in IndexedDB
```

Rules:

1. The tray generates `secret` (8 symbols, CSPRNG) **before** `pair_start` and composes the code `claim || secret` when it receives `pair_ready`. The code is valid until `pair_ready.expires_at` (server TTL, 5 min): the tray displays the countdown from that instant and discards the `secret` when it expires — it does not use a shorter timer of its own.
2. Exactly **one** `pair_join` per pairing session. Any failure (invalid MAC, malformed message, 60 s timeout between messages, expiry) → the tray sends `pair_done{ok:false}`, discards the `secret` and displays an error. A new pairing requires a new user action in the tray menu (it generates a new code).
3. The browser **only persists `PK`** after `pair_result{ok:true}` (and having already verified `cB`). The tray persists the pairing entry when it verifies `cA`, before sending `pair_done`.
4. A tray's first pairing **binds the device to the account** of the browser. Subsequent pairings (other browsers) are started from the tray menu ("Pair a device…", which also opens the local page with the code and a QR code) and follow the same flow; the server creates neither a new device nor a new token.
5. The server **never** starts a pairing and never asks the tray to display a code. (Tray rule 5: local actions only via the local menu.)

### 4.3 Derivation of the scalar `w`

```
pw = ASCII(normalize(code))                 # 12 symbols, uppercase, no hyphens (claim included)
w  = int_be(SHA-512(pw)) mod n              # n = order of P-256; 512 bits ≥ 256+64 → no bias (RFC 9382 §3.2)
```

No MHF: the secret has only 40 bits and the only attack is online (1 attempt per session); an MHF would add no security and would slow down pairing on the phone. Vector: `V1_pairing_code_to_w`.

### 4.4 SPAKE2 messages (inside `pair_msg.payload`)

| `t` | Direction | Fields |
|---|---|---|
| `pake1` | A→B | `v:1`, `pA: b64url(65 bytes)` |
| `pake2` | B→A | `v:1`, `pB: b64url(65 bytes)`, `cB: b64url(32 bytes)` |
| `pake3` | A→B | `v:1`, `cA: b64url(32 bytes)` |

Computation (RFC 9382 §3.3–§4, `h = 1` on P-256):

```
A: x ←$ [1, n)   X = x·G   pA = w·M + X
B: y ←$ [1, n)   Y = y·G   pB = w·N + Y
A: K = x·(pB − w·N)        B: K = y·(pA − w·M)
TT = len8le(A)||A || len8le(B)||B || len8le(pA)||pA || len8le(pB)||pB || len8le(K)||K || len8le(w)||w   (w = 32 bytes big-endian)
Ke || Ka = SHA-256(TT)                      (16 || 16 bytes)
KcA || KcB = HKDF-SHA256(ikm=Ka, salt=∅, info="ConfirmationKeys" || AAD, L=32)
cA = HMAC-SHA256(KcA, TT)    cB = HMAC-SHA256(KcB, TT)
```

Mandatory validation when receiving `pA`/`pB`: the point is **on the curve**, is not the point at infinity, and has a 65-byte encoding with prefix `0x04`. MACs are compared in constant time. B sends `cB` together with `pB` (saves a round trip; the RFC requirement — not to consider the exchange complete before verifying the peer's MAC — is kept).

Vectors: `V2_spake2_rfc9382_check` (first vector of the RFC's Appendix B, must pass in each side's library) and `V2_spake2_tunnelio` (Tunnelio's identities and AAD, `x`/`y` fixed **only** for the vector).

### 4.5 Pairing key

```
PK = HKDF-SHA256(ikm=Ke, salt=∅, info="tunnelio/v1/pairing-key", L=32)
```

`Ke` (16 bytes) is never used directly. Vector: `V3_pairing_key`.

### 4.6 `pairing_id`

```
pairing_id = SHA-256("tunnelio/v1/pairing-id" || PK)[0:16]
```

Derived on both sides without an extra message. The tray stores `{pairing_id → PK, created_at, label}`; the browser stores `{device_id → pairing_id, PK, name}`.

### 4.7 Storage

| Side | Where | Content |
|---|---|---|
| Tray | `<config>/pairings.json`, mode `0600` (Linux/macOS) / user ACL (Windows) | list of pairings. (The OS keyring is a possible improvement.) |
| Tray | `<config>/device.json`, `0600` | `device_id`, `device_token`, `server_url` |
| Tray | `<config>/` itself, `0700` (an existing folder open to other accounts is closed on start) | every file above, `history.sqlite` (§9) and `tray.log` |
| Browser | IndexedDB `tunnelio` → store `pairings` | raw `PK` (WebCrypto's HKDF requires a raw salt; IndexedDB is isolated per origin). |
| Browser → server (rev. 1.2) | `PUT /api/devices/pairings` (§10.2) | the same list, encrypted with a key derived from the login password; a new browser of the same account imports the pairings when signing in, without typing a code. |

**Unlinking (rev. 1.3).** `DELETE /api/devices/{id}`, changing the password and resetting the password delete the device row: the tray receives `revoked` and deletes `device.json` **and** `pairings.json`; the server deletes the pairings blob. The history on the computer stays intact; the user pairs again with the code from the tray.

## 5. E2E session handshake

Every session (`client_id`×`device_id`) begins with a 3-message handshake that produces **ephemeral** and **directional** keys. Reasons: forward secrecy (a leaked `PK` does not open past sessions) and sequential nonces without persistent state (counters reset in each session).

### 5.1 Messages (in `data.payload`, plaintext for the relay, but with no secret)

| `hs` | Direction | Fields |
|---|---|---|
| `hello` | C→D | `v:1`, `pairing_id: b64url(16)`, `eph_pub: b64url(32)` |
| `hello_ack` | D→C | `v:1`, `eph_pub: b64url(32)`, `mac: b64url(32)` (= `mac_d`) |
| `confirm` | C→D | `v:1`, `mac: b64url(32)` (= `mac_c`) |
| `reject` | D→C | `v:1`, `code` ∈ {`E_UNKNOWN_PAIRING`, `E_VERSION`, `E_BUSY`} |

The discriminator field is `hs`; envelopes (§6) do **not** have `hs`. A payload without `hs` and without `ciphertext` is invalid → discard.

### 5.2 Derivation

```
hello_c_bytes = 0x01 || pairing_id (16) || eph_pub_c (32)
hello_d_bytes = 0x01 || eph_pub_d (32)
th   = SHA-256(hello_c_bytes || hello_d_bytes)
ss   = X25519(eph_priv_self, eph_pub_peer)        # MUST reject an all-zero output (RFC 7748 §6.1)
prk  = HKDF-Extract(salt=PK, ikm=ss)              # = HMAC-SHA256(PK, ss)
k_c2d    = HKDF-Expand(prk, "tunnelio/v1/c2d"       || th, 32)
k_d2c    = HKDF-Expand(prk, "tunnelio/v1/d2c"       || th, 32)
k_conf_c = HKDF-Expand(prk, "tunnelio/v1/confirm-c" || th, 32)
k_conf_d = HKDF-Expand(prk, "tunnelio/v1/confirm-d" || th, 32)
mac_d = HMAC-SHA256(k_conf_d, th)     mac_c = HMAC-SHA256(k_conf_c, th)
```

Vector: `V4_session_handshake` (uses Alice's and Bob's private keys from RFC 7748 §6.1 as the ephemeral keys).

### 5.3 Rules

- The browser **MUST** verify `mac_d` before sending `confirm`. The tray **MUST** verify `mac_c` before accepting any envelope. An invalid `mac_c` or a malformed `hello` → **silent discard** and the session returns to the initial state (the browser MAY try again with a new `hello`; after 3 failures, it shows "pair again"). `reject` exists only for the listed codes.
- Unknown `pairing_id` → `reject{E_UNKNOWN_PAIRING}` (plaintext, needed for the UI to offer a new pairing).
- After verifying `mac_c`, the tray sends a `device_info` (§7.4) as the **first envelope**.
- The ephemeral private keys are erased after the derivation. Likewise `ss` and `prk`.
- A new `hello` in the same session replaces the state (the browser reloaded the page, for example).

## 6. Encrypted envelope

### 6.1 Format (in `data.payload`)

```json
{ "v": 1, "device_id": "<uuid>", "nonce": "<b64url 12 bytes>", "ciphertext": "<b64url ct||tag>" }
```

### 6.2 Construction

```
nonce = dir (1 byte) || 0x00 0x00 0x00 || counter (8 bytes big-endian)
        dir = 0x00 for C→D (key k_c2d) · 0x01 for D→C (key k_d2c)
aad   = 0x01 || device_id_raw (16 bytes)
ciphertext||tag = AES-256-GCM(key_dir, nonce, aad, plaintext)     # plaintext = UTF-8 JSON of the message (§7)
```

### 6.3 Rules

- `counter` starts at **0** in each direction of each session and is incremented by 1 per envelope sent. The receiver keeps `expected` and accepts **only** `counter == expected` (no window: the relay delivers in order per connection). Out of order = replay or loss → the receiver **discards the envelope, logs it and ends the session** (`close` on the relay), forcing a new handshake (§5).
- Counter limit: `2^53 − 1`. Reached → close the session.
- Authentication failure (invalid tag, `device_id` different from its own, unknown `v`) → **discard silently and log** (rule 7). Never reply to an envelope that does not decrypt.
- Size: `plaintext` ≤ 8 MiB (§0.3); there is no fragmentation — neither side splits a message across envelopes, and a larger message is an application error (§7.6).

Vector: `V5_envelope` (three envelopes: C→D counters 0 and 1, D→C counter 0).

- Every message is a JSON object with `type` and, when it is a request or belongs to a request, `id`.

### 7.7 Documents in the chat (rev. 1.4)

The tray does not change: documents are converted **in the browser** and travel inside an ordinary `chat`.

- **Formats:** PDF (`pdf.js`), Word `.docx` (`mammoth`), spreadsheets `.xlsx`/`.xls`/`.ods`/`.csv` (SheetJS), text/Markdown/code/JSON. The original file is never sent; input limit 50 MB.
- **Format in the message:** the extracted text goes in the `content` of the `user` message, before the typed request: `<document name="…" kind="pdf|docx|sheet|text" pages="N">…</document>` (one block per document; `name` escaped). The UI recognizes the blocks, including in the history, and shows an expandable *chip* instead of the text.
- **Figures (automatic mix):** the text of all pages goes as text; if the model has the `vision` capability, the pages with figures and the pages without text (scanned) also go as images (JPEG, side ≤ 1600 px), within the limit of §0.3 (4 per message, counting the attached photos). Model without vision + document with figures → warning; scanned-only PDF + model without vision → sending blocked.
- **Model memory** (rev. 1.9 rule): estimate `ceil(characters / 3.5)` of the whole conversation + 2048 for the response (at most a quarter of the model's `context_length`). Ollama picks a model's context when it loads it (by the computer's video memory: 4k under 24 GiB, 32k up to 48 GiB, 256k above; or the Ollama app's setting / `OLLAMA_CONTEXT_LENGTH`), never grows it during a conversation (what does not fit is cut from the start, silently) and **reloads the model whenever `num_ctx` changes**. So, before every `chat`, the browser asks `list_running` for the context the model is loaded with (`context_length`, when Ollama reports it): (1) above the model's `context_length`, sending is blocked with a warning; (2) loaded with *L* ≥ estimate → `options.num_ctx = L` (Ollama's own choice is kept; an equal value does not reload); (3) not loaded and estimate ≤ 4096 → no `num_ctx` (Ollama's choice, never below 4k); (4) otherwise `num_ctx` = the power of two ≥ estimate (8k, 16k, 32k…), capped at the model's `context_length` — one reload, rarely another. No hardware logic in Tunnelio: what fits in memory stays Ollama's call. Until rev. 1.8 the rule sent `num_ctx` in steps of 2048 above 4096, which on computers whose default is 32k or 256k shrank the context and reloaded the model at every step.
- The message is still limited to 8 MiB (§0.3). In the computer's history the text stays in the message and the image pages go in `message_images`, like photos.

| `stop` | string[] | ≤ 8 items, each ≤ 64 B |

Any other key in `options` → `E_INVALID`. (`num_gpu`, `num_thread`, `use_mmap`, `main_gpu`, etc. are machine settings: they stay out of the channel.)

**In the interface (rev. 1.6):** the model menu, below the message box, has "Model settings…" with `temperature`, `top_p`, `top_k`, `num_predict`, `repeat_penalty` and `seed`, stored **in the browser, per model name** (`settings.model_options`); an empty field = the model's own default; "Default" forgets everything. The browser validates the ranges above before storing, and only sends `options` when something is set (besides `num_ctx`, §7.7). `think` only goes to models whose `show_model` announces `thinking` in `capabilities` (Ollama refuses `think` for the others); its switch is in the same menu. `num_ctx` and `stop` have no field in the interface.

### 8.4 Streaming

Ollama responds with NDJSON. For each line: `message.content` and `message.thinking` accumulate in a buffer; every ≥ 40 ms (or when `done:true` is received) the tray emits `chat_chunk`. On the final line (`done:true`) it emits `chat_done` with `done_reason` (`stop`/`length` from Ollama; `abort` if cancelled; `error` on failure) and `stats`. The HTTP body is limited to 64 MiB per response; lines > 1 MiB abort with `E_OLLAMA_ERROR`.

### 8.5 Detection and local actions (rules 5 and 9)

States: `running` (`/api/version` 2xx), `stopped` (binary found in the PATH/default locations, no response), `not_installed`. Actions **only in the tray menu**: start/restart Ollama, open the download page, change the Ollama host/port, change the relay server, autostart (opt-in on the first run — rule 10), pair a browser, remove pairings, remove the device (unlinks and deletes `device.json`), quit. `internal/system` is the **only** package that imports `os/exec` (verified by `depguard` in `.golangci.yml` and by an imports test).

**Local pages (rev. 1.2).** Tray menus do not show images or forms, so the tray serves two pages at `http://127.0.0.1:<random port>/…?t=<random 24-byte token>` (`internal/localui`): **pairing** (code, QR with the link `<server>/pair#<code>`, countdown, instructions, "generate new"/"cancel" buttons) and **settings** (server, Ollama address, computer name, autostart). *Loopback* only, no token → 404, POST only *same-origin*, CSP with no external origins; nothing is fetched from the network. The menu items open these pages in the default browser. The item with the code copies it to the clipboard when clicked.

## 9. Private history (tray)

Default. Source of truth: SQLite in the tray (`<config>/history.sqlite`, driver `modernc.org/sqlite`, no CGO, WAL), which also stores the agents and the skills (rev. 1.8, §9.4). Associated with the **device** — any browser paired with it sees the same history. The server persists none of this.

The file is **not encrypted**: it is protected by the system account. On Linux and macOS the tray keeps the config folder at `0700` and `history.sqlite` (with its `-wal` and `-shm`) at `0600`, and closes a folder or file that an older version left readable by other accounts; on Windows the user profile's ACL does the same.

### 9.1 Schema

```sql
CREATE TABLE conversations (
  id            TEXT PRIMARY KEY,          -- UUID (generated by the browser)
  title         TEXT NOT NULL,
  model         TEXT NOT NULL,             -- last model used
  created_at    TEXT NOT NULL,             -- ISO 8601 UTC
  updated_at    TEXT NOT NULL,
  message_count INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE messages (
  id              TEXT PRIMARY KEY,        -- UUID (generated by the tray)
  conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  seq             INTEGER NOT NULL,        -- 1, 2, 3… per conversation
  role            TEXT NOT NULL CHECK (role IN ('system','user','assistant')),
  content         TEXT NOT NULL,
  thinking        TEXT,
  model           TEXT,
  stats_json      TEXT,                    -- stats from chat_done (assistant)
  aborted         INTEGER NOT NULL DEFAULT 0,
  created_at      TEXT NOT NULL,
  UNIQUE (conversation_id, seq)
);
CREATE INDEX idx_conversations_updated ON conversations(updated_at DESC);
CREATE TABLE message_images (                 -- rev. 1.1 (schema_version 2)
  message_id TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  idx        INTEGER NOT NULL,
  mime       TEXT NOT NULL,
  data       BLOB NOT NULL,
  PRIMARY KEY (message_id, idx)
);
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);  -- schema_version = 4
-- rev. 1.8 (schema_version 3): conversations gains agent_id TEXT and skill_ids TEXT (JSON), added
-- in place in an old file; and the agents and skills tables:
CREATE TABLE agents (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, description TEXT NOT NULL, icon TEXT NOT NULL,
  model TEXT NOT NULL, instructions TEXT NOT NULL, options_json TEXT, think INTEGER,
  skills_mode TEXT NOT NULL CHECK (skills_mode IN ('off','all','selected')), skill_ids TEXT NOT NULL,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE skills (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, description TEXT NOT NULL, category TEXT NOT NULL,
  instructions TEXT NOT NULL, created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
-- rev. 1.9 (schema_version 4), columns added in place: agents.chain TEXT (JSON array of agent ids)
-- and messages.chain_json TEXT (JSON [{agent_id, name, model, content}] on an assistant message).
```

### 9.2 Write rules

- In a `chat{mode:"private"}`: if the conversation does not exist, it is created with `title` (or the first 60 characters of the last `user` message) and `model`. The tray inserts **only the last `user` message** of the array (the previous ones are already recorded) and, when finished, the `assistant` message (with `aborted=1` if aborted, partial content preserved). It updates `updated_at`, `message_count`, `model`.
- The browser always sends the complete `messages[]` (Ollama is stateless); the tray does **not** reconcile divergences — *append-only* (no editing nor regenerating).
- `chat{mode:"private"}` always records; `chat{mode:"incognito"}` (rev. 1.6) creates no conversation and records no message at all — the anonymous chat exists only in the browser tab and disappears on leaving.
- `history_delete` deletes in cascade. Deleting the device through the local menu deletes the file.
- In a `chat{mode:"private"}` the tray records, on each turn, the `agent_id` and the `skill_ids` received (absent = none). The `system` message the browser sends is **not** recorded.

### 9.3 (removed)

Conversations kept in the cloud existed from rev. 1.2 to rev. 1.3 and were removed; the number stays free so that the references to §9.4 remain valid.

### 9.4 Agents and skills (rev. 1.8)

They live **on the computer**, in the same file as the conversations: each computer has its own; with the computer turned off they cannot be seen or edited; `history_clear` does not delete them; the server only forwards the encrypted channel.

- **Agent:** `name` (1–80 characters, no control characters), `description` (≤ 300), `icon` (name from the app's icon gallery, `^[a-z0-9]+(-[a-z0-9]+)*$`, ≤ 40), `model` (valid name, §8.2), `instructions` (≤ 32 KiB), `options?` (the same rules as §8.3; the tray stores the already-validated object), `think?` (bool), `skills` ∈ {`off`,`all`,`selected`} and `skill_ids` (≤ 100 UUIDs, no repeats). At most **100 agents** per computer.
- **Skill:** `name` (1–80), `description` (≤ 500; says when the skill applies), `category` ∈ {`""`, `ideas`, `travel`, `learning`, `writing`, `shopping`, `code`, `misc`, `roleplay`, `finance`}, `instructions` (markdown, ≤ 32 KiB). At most **100 skills** per computer.
- **In the chat** (the browser assembles it, the tray does not): with an agent, the model, the settings (`options`) and the thinking (`think`, only if the model announces `thinking`) are the agent's. The skills that go along are the agent's (none, all of the computer's, or the selected ones) plus those turned on in the conversation. The `system` message, the first of `messages[]` on every turn, is: the agent's instructions; then `# Skills` and, for each skill, `## name`, `When to use: description` and the **full text** of the instructions. With neither an agent nor a skill, there is no `system` message. The `agent_id` and the `skill_ids` (only those turned on in the conversation) go in the `chat` for the tray to record; reopening the conversation applies the agent and the skills again **as they are now**. A deleted agent becomes "No agent". If the agent's model is not installed on the computer, sending is blocked with the warning.
- **Agent chain** (rev. 1.9, capability `chain`; Advanced → Chain in the agent editor): an agent can name up to **5** other agents that answer after it, in order (`agent.chain`; deleting an agent takes it out of every chain). In a chat with that agent, the **browser** runs the chain: the chosen agent answers first, then each next one, each with its own model, settings, thinking and skills (plus those turned on in the conversation) and the conversation as it is; every agent after the first gets in its `system` message a note — it is agent *k* of *n*, build on the previous answer, do not mention the chain — and the **previous agent's answer** (`<previous_answer agent="name">…</previous_answer>`). The agents before the last one answer in anonymous chats (`mode:"incognito"`, nothing is recorded); the last one answers in the conversation's own `chat`, with `chain:[{agent_id, name, model, content}]` = the earlier answers, which the tray keeps with the assistant message (`messages.chain_json`) and returns in `history_get`. The interface shows each earlier answer folded above the reply, like the thinking ("Agent 1 of 2: name"). The reply's model is the last agent's. A chain stopped (or failed) before its last agent records nothing. Chains are not nested: an agent of the chain answers alone, its own chain is ignored. If the model of any agent of the chain is missing on the computer, sending is blocked with the warning. Each agent loads its own model, so a chain multiplies the time of an answer.

## 10. Single password, pairing synchronization and second factor

Since rev. 1.3 the conversations live **only on the user's computer** (§9): there is no vault and no cloud storage of conversations. What remains on the server is one opaque blob per account with the pairings (§10.2), so that a new browser gets in with just the password.

### 10.1 Keys (rev. 1.2/rev. 1.3)

```
email_norm   = UTF-8(lower(trim(email)))
salt         = SHA-256("tunnelio/auth/v1" || email_norm)[0:16]
master       = Argon2id(password = UTF-8(NFC(password)), salt, m = 65536 KiB, t = 3, p = 1, tagLength = 32)
auth_key     = HKDF-SHA256(ikm = master, salt = ∅, info = "tunnelio/auth/v1/login", L = 32)
pairings_key = HKDF-SHA256(ikm = master, salt = ∅, info = "tunnelio/auth/v1/pairings", L = 32)
```

- The server **only sees `auth_key`** (base64url without `=`, 43 characters) in the `password` field of `register`, `login`, `change-password`, `password-reset/confirm`, `totp/disable` and `DELETE account`; it applies Django's *hasher* on top. The real password never leaves the browser. Vector: `V8_login_keys`.
- Deterministic `salt` per e-mail: the browser derives everything **before** talking to the server. Changing the e-mail does not exist in v1.
- `pairings_key` stays in memory while the session is open and disappears on signing out. (rev. 1.2's `vault_kek` no longer exists.)
- Accounts created in rev. 1.2 had a `VaultConfig`; rev. 1.3 deletes the table. Cloud conversations did not exist in production when rev. 1.3 went in.

### 10.2 Pairing synchronization

An account's pairings (§4.7) travel between browsers as **one** blob:

```
plaintext = {"version":1, "pairings":[{"device_id", "pairing_id": b64url(16), "pk": b64url(32), "name", "created_at"}]}
stored    = nonce(12, random) || AES-256-GCM(key = pairings_key, nonce, aad = "tunnelio/pairings/v1", pt = plaintext)
```

| Method and route | Body / response |
|---|---|
| `GET /api/devices/pairings` | `200 {timestamp, ciphertext, updated_at}` or `404` |
| `PUT /api/devices/pairings` | `{timestamp, ciphertext: b64url}` → `201`/`200`; `413 E_TOO_LARGE` above **64 KiB** |
| `DELETE /api/devices/pairings` | `204` |

- After login, the browser downloads the blob, merges it with IndexedDB by `device_id` (the newest `created_at` wins), discards entries for devices that no longer exist in the account and rewrites the blob if something changed. A blob that does not open (password changed) counts as empty.
- Consequence: **one pairing per computer, per account**. The first browser pairs with the code; the other browsers of the same account receive the `PK` through synchronization. "Forget paired devices" in the tray invalidates the `PK` for all of them.
- The server sees only size and dates (the admin too, §11.3). Rate: `pairings_write: 60/min`.

### 10.3 Changing or resetting the password disconnects everything (rev. 1.3)

A single rule, easy to explain: **the password changed, pair again.** `change-password` and `password-reset/confirm` delete all the account's devices (each tray receives `revoked` and deletes `device.json` + `pairings.json`) and the pairings blob; the reset also turns off the second factor. The other browser sessions drop. The history on the computer is not touched. There is no recovery code and no copy of the key anywhere: the login password is the only credential.

### 10.4 Optional second factor (TOTP, rev. 1.3)

- Turn on in *Settings → Security*: `POST /api/auth/totp/setup` → `{secret (base32), otpauth_url}` (the browser shows the QR); `POST /api/auth/totp/enable {code}` confirms. `me.totp_enabled`.
- Login: `POST /api/auth/login` with `totp_code`; without a code → `401 E_TOTP_REQUIRED`; wrong → `401 E_TOTP_INVALID`; 5 errors → 15-minute lockout (`E_TOTP_LOCKED`). Window ±1 step of 30 s; an accepted step is not accepted again (anti-replay).
- Turn off: `POST /api/auth/totp/disable {password, code}`.
- Lost the authenticator: "Forgot your password?" (§11.2) turns off the second factor along with everything else. No recovery codes.
- In the database the seed is stored encrypted (Fernet with a key derived from `SECRET_KEY`); a *dump* alone does not generate codes.

### 10.5 Synced preferences and active sessions (rev. 1.7)

**Preferences** (the person's, not the device's): theme, language, dictation, reasoning, default model, settings of each model, pinned conversations and "What should Tunnelio call you?" (`display_name`, ≤ 40 characters; empty = what comes before the `@`). They travel between browsers as **one blob** sealed in the browser with the same `pairings_key` (§10.1) and **a different AAD**, so one blob never opens as the other:

```
stored    = nonce(12) ‖ AES-256-GCM(pairings_key, nonce, aad = "tunnelio/preferences/v1", plaintext)
plaintext = {"version":1,"updated_at":ISO,"prefs":{theme, language, dictation, think, default_model, model_options, pinned_conversations, display_name}}
```

`GET/PUT/DELETE /api/auth/preferences` (same format as the pairings blob, ≤ 32 KiB); the server stores it and does not read it. The browser keeps its own copy (it opens instantly, without flicker) and treats the account's copy as the reference: on signing in or opening the app, it pulls and applies it; without a readable blob, the local copy becomes the account's; on each change, it sends (after a 0.8 s wait) merging with what other browsers changed (only the keys changed here overwrite); keys that have not yet reached the account are kept in the browser (`preferences.pending`), so reloading or closing the tab before the send does not lose the change (the next opening sends it), and hiding the tab sends immediately; a change made during a send waits for the next one and is never undone by the account's copy; on returning to the tab after 1 min, it pulls again. On signing out, the person's preferences go back to the defaults in that browser. Password change: the browser seals again with the new key. **Password reset: the server deletes the blob** (no one can open it anymore) and the preferences start over from the browser in which the person signs in. **They remain only in the browser** (they belong to the device): default computer, sidebar pinned or not, dictation notice.

**Active sessions**: each signed-in browser (Django session) has a `LoginSession` row with what the browser itself announces in the `User-Agent` (browser, system, kind: computer, phone, tablet), created at and last use. **No IP and no location.** `GET /api/auth/sessions` lists them (marking the current one); `DELETE /api/auth/sessions/{id}` ends one (ending the current one is a logout); `POST /api/auth/sessions/logout-all` ends all of them, including the current one. Ending deletes the Django session **and immediately closes** that browser's WebSocket (group `login.row.<row id>`; session without a row: `login.key.<sha256(session_key)[:32]>`; close 4001). Changing the password ends the others; the current one continues with the same row and the same WebSocket (Django rotates the session key and the row follows it); resetting ends all of them. The row disappears with the session; the daily purge cleans up the expired ones.

## 11. Backend — data model and REST API

### 11.1 Apps and models

**`accounts`**
- `User` (custom, `USERNAME_FIELD = email`): `email` (unique, *case-insensitive*), `password` (Argon2id via `Argon2PasswordHasher` over the `auth_key`, §10.1), `is_active` (**false until the e-mail is confirmed**, when `EMAIL_URL` is set), `is_staff`, `created_at`, `last_login`.
- `EmailCode` (rev. 1.3): `user`, `purpose` ∈ {`verify`,`reset`}, `code_hash` (HMAC-SHA256 with `SECRET_KEY`), `created_at`, `expires_at`, `attempts`, `used`.
- `TotpSecret` (rev. 1.3): `user` (OneToOne), `secret_enc` (Fernet), `confirmed`, `created_at`, `last_step`, `failed_attempts`, `locked_until`.
- Sessions: `django.contrib.sessions` in the `sessionid` cookie (`Secure`, `HttpOnly`, `SameSite=Lax`, 14 days, renewed on every request). Django's default CSRF (cookie + `X-CSRFToken` header).
- `LoginSession` (rev. 1.7): `user` (FK, `CASCADE`), `session_key` (unique; never displayed, not even in the admin), `browser`, `os`, `device` ∈ {`computer`,`phone`,`tablet`,`other`}, `created_at`, `last_seen_at` (touched at most every 5 min). No IP, no location (§10.5).

**`devices`**
- `Device`: `id` (UUID, pk), `user` (FK, `CASCADE`), `name` (≤ 64), `platform`, `tray_version`, `token_hash` (SHA-256 hex, unique), `created_at`, `last_seen_at`. Revoking = **deleting the row** (the token stops authenticating). Presence does **not** go to the database (Django cache: LocMem or Redis).
- `PairingSession`: `claim` (4 symbols; unique among the active ones), `device` (FK null = new device), `user` (FK null until `pair_join`), `state` ∈ {`waiting`,`joined`,`done`,`failed`,`expired`}, `device_channel`, `client_channel`, `created_at`, `expires_at`. Cleanup by the `purge_relay_logs` command (and in the consumer itself on expiry).

**`pairings`** (until rev. 1.4 it was called `vault`; the `pairings.0001` migration adopts the old table)
- `PairingsBlob`: `user` (OneToOne), `timestamp` (from the client), `ciphertext` (Binary, ≤ 64 KiB), `size`, `updated_at`. Served at `/api/devices/pairings` (§10.2).

**`catalog`** (rev. 1.6)
- `OllamaCatalog`: `key` (pk, `"ollama"`), `source_url`, `fetched_at`, `data` (JSON: list of `{name, description, capabilities[], sizes[], pulls, pulls_text, tags, updated_at, updated_text, size_bytes?}`), `count`. Filled by `manage.py refresh_ollama_catalog` (the entrypoint runs it at startup and every 24 h): it reads the public page `ollama.com/library?sort=popular` (HTML; there is no API), classifies the labels by their text (`tools`, `vision`, `thinking`, `embedding`, `cloud`; sizes `1b`, `e4b`, `8x7b`…) and rejects pages with fewer than 50 entries (the previous list stays). **rev. 1.9:** the list is stored, then each model's own page (`ollama.com/library/<name>`), one per second, gives `size_bytes` — `{tag: [smallest, largest]}` in bytes (decimal units, as the library writes them) for each size and `latest`; a range when the tag has one variant per platform (e.g. `gemma4:e4b`, 6.6–9.5 GB); a tag with no size (the cloud ones) is left out. Only the pages of models that are new or whose `updated_at` or `sizes` changed are read (the others keep their sizes; the whole library takes about four minutes the first time); a page that fails, or yields no size where sizes were known, keeps the previous values, and 5 failures in a row stop until the next run. The web app shows the size in each size pill of the library ("3b · 2 GB") and on the Download button of "Other models" (its `latest`; for a model whose page shows no `latest`, its first size, which that button then downloads), and nothing while it is unknown. `catalog/data/ollama-library.json` is the embedded copy, served until the first fetch succeeds: it keeps the facts (names, labels, sizes, counts, dates) but not the descriptions, which are ollama.com's own text and come only from a live fetch (until then the library shows none). No user data goes through here.

**`preferences`** (rev. 1.7)
- `PreferencesBlob`: `user` (OneToOne), `timestamp` (from the client), `ciphertext` (Binary, ≤ 32 KiB), `size`, `updated_at`. Served at `/api/auth/preferences` (§10.5); the admin shows only size and dates.

**`relay`**
- `ConnectionLog`: `user` (FK, `CASCADE`), `device` (FK null, `SET_NULL`), `kind` ∈ {`client`,`device`}, `connected_at`, `disconnected_at`, `bytes_in`, `bytes_out`, `frames_in`, `frames_out`, `close_code`. Retention: the `purge_relay_logs --days 7` command + a daily task in the process (idempotent); the same command deletes expired `EmailCode`s and accounts that never confirmed their e-mail (`UNVERIFIED_ACCOUNT_TTL_DAYS`, 7).

### 11.3 Admin

`/<ADMIN_URL_PATH>/` (default `admin`; keep it off the public hostname, as `deploy/` does: its own port on loopback, behind a private network). Registered: `User` (email, dates, `is_active`), `Device` (name, platform, version, dates; `token_hash` hidden), `PairingSession` (claim, state, dates; read-only), `pairings.PairingsBlob` and `preferences.PreferencesBlob` (size, dates; ciphertext hidden; read-only), `ConnectionLog` (read-only) and `OllamaCatalog` (source, count, date; read-only). The e-mail codes and the second-factor seeds are not in the admin. No bulk action that reads content.

### 11.4 Serving the SPA

Self-host: `web/dist` is copied into the server image; `whitenoise` serves `/assets/*` with an immutable cache and `index.html` for any non-API route (SPA fallback). In production `nginx` serves the web app from its own image (the public site has a container of its own), with the same cache and fallback rules, and forwards `/api` and `/ws` to the server. `/pair#...` and the other routes belong to the client router.

Next to the bundle (never inside it) the image writes `/version.json` = `{"revision": "<commit>"}`, the public commit it was built from, served without cache. The bundle depends only on the code, so rebuilding it from that commit with the same recipe gives the same files (`scripts/verify-build.sh`); Settings → General shows the commit as *Build*.

## 12. Versioning and compatibility

- `v` appears in: the relay's `hello`/`welcome`, SPAKE2 messages, handshake, envelope. All at `1`.
- The tray announces `protocol_versions` in `hello` (relay) and in `device_info`; the browser chooses the **highest one in common**; no intersection → `reject{E_VERSION}` and the UI asks for a tray update.
- **Forward compatible:** new fields can be added without a bump; receivers ignore unknown ones. New message types **require** an entry in the allowlist (tray) and, since they are ignored by old versions, can be added without a bump as long as they are optional.
- **Bump of `v`** for any change to the byte layout, derivation, AEAD or semantics of an existing field. The relay is agnostic to `v` (it only requires an integer ≥ 1).
- **rev. 1.2/rev. 1.3 without a bump:** the login derivation (§10.1) is between the browser and the REST server, not part of the channel; the pairings blob is a REST resource; optional types enter and leave the allowlist through `capabilities` (rev. 1.3 removed `history_import`).
- Tags: `vX.Y.Z` (tray; pure semver, required by GoReleaser) and `server/vX.Y.Z` (server image). `web/` is versioned together with `server/` (same image). Policy: the site MUST support the tray's protocol version **N−1** for ≥ 6 months after a bump.

## 14. Decisions and rationale

### 14.1 SPAKE2 with a short code (chosen) vs. a 32-byte key (QR/base32)

| | SPAKE2 + 12-symbol code | 32-byte key |
|---|---|---|
| UX | Type 12 symbols (or QR→URL). Works on a phone, a laptop or a work computer, looking at the computer's screen. | 53 symbols: infeasible to type; QR requires a camera in the browser (lib + permission) or being on the same computer. |
| Security | 40 bits + PAKE: online attack only, 1 attempt per code; a malicious server wins with probability 2^−40 per session. | 256 bits, nothing to guess. |
| Cost | ~150 lines per side on top of audited curve libraries + the RFC vectors. No ready-made, maintained SPAKE2/RFC 9382 library existed in Go **and** TS when this was decided. | ~0 new crypto. |
| Decision | **Yes.** The UX is the product. The cost is contained and verifiable by vectors. | Documented fallback. |

### 14.2 P-256 instead of edwards25519 in SPAKE2

RFC 9382 vectors exist **only** for P-256. With two independent implementations, official vectors are worth more than the elegance of Ed25519. P-256 has cofactor 1 (no `h·` step), and both ecosystems have audited point arithmetic: Go `filippo.io/nistec` (the same code as the stdlib's `crypto/ecdh`), TS `@noble/curves` 2.x (audited). X25519 remains the session curve (§5) — there, there are no vectors to take advantage of, and X25519 is simpler and is in Go's stdlib.

### 14.3 AES-256-GCM instead of XChaCha20-Poly1305

AES-GCM is in WebCrypto (hardware-accelerated, no library) and in Go's stdlib. The argument in favor of XChaCha (192-bit nonce for random nonces) does not apply: we use **sequential nonces** per session, and ephemeral keys reset the counter on each connection. In the vault of rev. 1.2 (removed in rev. 1.3 together with cloud storage) the nonces were random, but with a **per-conversation subkey** the number of encryptions per key stayed orders of magnitude below the 2^32 limit; today random nonces are used only for the sealed pairings and preferences blobs (§10), one encryption per change.

### 14.4 X25519 via a library, not WebCrypto

`crypto.subtle` only gained X25519 in Chrome 133 (Feb/2025) and Firefox 130; its status in stable Safari could not be confirmed. `@noble/curves` covers all browsers and is already a dependency (P-256). WebCrypto is kept for AES-GCM, HKDF/HMAC (SHA-256) and `getRandomValues`.

### 14.5 uvicorn instead of daphne

Same ASGI; Channels states that any conforming ASGI server works. uvicorn is faster and widely used and documented, and daphne brings nothing that is needed (HTTP/2 is terminated by the proxy in front). Explicit restriction: `UVICORN_WORKERS=1` with `InMemoryChannelLayer`; > 1 only with `REDIS_URL`.

### 14.6 Django 5.2 LTS + Channels 4.3

Django 5.2 is LTS until April/2028 (6.0 came out in Dec/2025; 6.2 LTS comes in Apr/2027). Channels 4.3.2 + `channels_redis` 4.3 (the only official *layer* for production).

### 14.7 React + Vite (chosen) vs. Svelte

Svelte would be lighter (Hollama proves that a pure Svelte SPA for Ollama fits in little code). But: React 19 + Tailwind v4 + shadcn/ui + Zustand is a well-trodden stack, with documented components, patterns and pitfalls; the React chat UI ecosystem is larger (`assistant-ui`, MIT, with an *external store runtime* for custom transport); and the SPA is served statically by the container (Vite generates `dist/`). Cost of switching frameworks > gain.

### 14.8 Chat interface: build on shadcn/ui (not Open WebUI)

- **Open WebUI is not suitable** either as a base or as an architecture reference: (a) it is SvelteKit + a FastAPI backend that **reads the content** (incompatible with a blind server); (b) the frontend depends on ~29 API modules of its own backend — reusing it as an E2E client means rewriting everything; (c) since v0.6.6 (Apr/2025) the license is its own, non-OSI, with a clause that forbids removing the branding above 50 users/30 days.
- **Hollama** (MIT, Svelte 5, 100 % in the browser) is the best **UX reference** for managing models/pull/sessions — worth copying flows, not code.
- Decision: our own screens with shadcn/ui + `react-markdown`/`remark-gfm`/`rehype-highlight`.

## 15. Out of scope and hooks for v2

Out of v1: sharing a device between accounts, routing across multiple devices, tool calling, native apps, LM Studio (port 1234, compatible API), billing, editing/regenerating messages, renaming a private conversation (needs `history_rename` in the allowlist).

Hooks left in place:

- **OpenAI-compatible API (v2):** `/ws/client` will accept `Authorization: Bearer <api_token>` (per-user tokens in `accounts.ApiToken`). An API client (the `tunnelio` CLI or an SDK) would do the **same** E2E handshake as the browser — the server stays blind. An HTTP API served by the server **cannot** be E2E; if one ever exists, it will be explicitly opt-in and documented as "the server sees the content".
- **Relay as a Go sidecar:** the interface of §3.9.
- **Binary framing** in the relay (binary frames with a fixed header) to cut the cost of base64/JSON — a change only in the relay and at the edges, envelope `v` unchanged.
- **LM Studio:** `internal/ollama` gains a sibling implementation with the same fixed table; `device_info.capabilities` announces `"backend":"lmstudio"`.
